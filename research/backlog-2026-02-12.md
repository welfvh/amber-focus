## 3. Re-blocking Reliability Audit

Confirm that when a timed allowance expires, sites are actually inaccessible again.

Current re-blocking path (server `checkAllowanceExpiry` every 30s):
1. `enableBlocking(getEffectivelyBlockedDomains())` — rewrites `/etc/hosts` via daemon
2. Daemon's own `checkAllowanceExpiry` (also 30s) — `refreshBlocking()` + `blockDomainIPs()` + `killConnectionsToDomain()` + `closeBrowserTabs()`

Potential gaps to audit:
- **Race condition**: server and daemon both check independently with different state. Server manages allowances in JSON file, daemon manages its own `state.allowances`. Are they always in sync?
- **DNS cache**: `flushDnsCache()` runs, but browsers (especially Chrome) cache DNS internally. May need proxy-level enforcement.
- **Existing connections**: `pfctl -k` kills TCP state, but WebSocket/HTTP2 long-lived connections may survive if pf rules aren't in place yet.
- **Tab closing**: AppleScript tab closing depends on browser being scriptable. Arc/Chrome/Safari covered, but what about Firefox or Brave?
- **Server-only path**: when server's `checkAllowanceExpiry` fires, it only calls `enableBlocking()` (hosts + DNS). It does NOT call `enforceBlockViaDaemon()` (IP block + connection kill + tab close). The daemon does this independently, but timing may differ.

Deliverable: test each gap, fix any found, document results.
